# План E2E бизнес-тестов (Сквозное тестирование)

## 1. Цель тестирования

Проверка полного бизнес-цикла обработки дела от момента регистрации вызова до сохранения отчета в ЦБД через пользовательский интерфейс.

**Инструменты**: Selenium WebDriver, Cypress, Testcontainers (PostgreSQL)
**Окружение**: Изолированная тестовая среда с полным стеком (Frontend + Backend + БД)

---

## 2. Идентификация бизнес-цикла

### 2.1 Ключевой сценарий (Main Business Flow)

**Полный цикл обработки дела**:
```
1. Регистрация вызова диспетчером (UC1)
   ↓
2. Автоматическое назначение ресурсов системой (UC5)
   ↓
3. Корректировка состава отряда диспетчером (UC7)
   ↓
4. Предоставление доступа участникам (UC6, UC8)
   ↓
5. Сбор улик андроидом-следователем (UC2)
   ↓
6. Подтверждение улик офицером (UC2)
   ↓
7. Формирование шаблона отчета офицером (UC3)
   ↓
8. Сохранение отчета в ЦБД системой (UC12)
   ↓
9. Уведомление участников об изменениях (UC4)
   ↓
10. Просмотр данных всеми участниками (UC9, UC11)
    ↓
11. Логирование всех действий (UC10)
```

### 2.2 Охват Use Cases
- **Основные**: UC1, UC2, UC3, UC5, UC7, UC12
- **Вспомогательные**: UC4 (уведомления), UC6/UC8 (доступ), UC9 (чтение), UC10 (логирование), UC11 (ЦБД)

---

## 3. Подготовка тестового окружения

### 3.1 Инфраструктура
**Используем Testcontainers для изоляции**:
- PostgreSQL контейнер (идентичный production окружению)
- Backend приложение (Micronaut JAR)
- Nginx (reverse-proxy)
- Frontend (React Router 7)

### 3.2 Тестовые данные
**Загружаются через SQL скрипты**:
- Пользователи с разными ролями:
  - `dispatcher` (диспетчер) - создание инцидентов
  - `officer_1`, `officer_2` (офицеры) - работа с делами
  - `investigator_1` (следователь) - сбор улик
  - `admin` - администратор системы
- Права доступа (permissions) для каждой роли
- Тестовые координаты локаций
- Справочники (positions, типы инцидентов)

## 4. Сквозное тестирование бизнес-сценария

### 4.1 Сценарий 1: Полный цикл обработки дела

#### Шаг 1: Регистрация вызова (UC1)
**Актор**: Диспетчер
**Действия**:
1. Авторизация в системе (`dispatcher`)
2. Переход на `/incidents/create`
3. Заполнение формы:
   - Reason: "Кража из магазина на ул. Невская 15"
   - Type: "Кража"
   - Location: (59.9311, 30.3609, 10.0)
   - Applicant: "Администратор магазина"
4. Установка "Wait for Assignment" = false (создать дело сразу)
5. Нажатие "Submit"

**Проверки**:
- Инцидент создан в БД
- Редирект на страницу инцидента
- Время выполнения < 60 сек

---

#### Шаг 2: Автоматическое назначение ресурсов (UC5)
**Актор**: Система + Диспетчер
**Действия**:
1. На странице создания дела автоматически отображается список ranked users
2. Пользователи ранжированы по:
   - Расстоянию от места инцидента (3D формула)
   - Загруженности (количество активных дел)
   - Соответствию позиции

**Проверки**:
- Ranked users загружены
- Сортировка корректна (ближайшие сверху)
- Отображены метрики (distance, active cases, score)

---

#### Шаг 3: Корректировка состава отряда (UC7)
**Актор**: Диспетчер
**Действия**:
1. Выбор 3 офицеров из топ-5 ranked users
2. Назначение позиций:
   - officer_1 → PATROL
   - officer_2 → INVESTIGATOR
   - investigator_1 → FORENSICS
3. Заполнение:
   - Case Title: "Расследование кражи в магазине"
   - Case Description: "Кража товаров на сумму 50000р"
4. Нажатие "Submit"

**Проверки**:
- Дело создано в БД
- Участники добавлены с правильными позициями
- Редирект на `/cases/{id}`

---

#### Шаг 4: Предоставление доступа участникам (UC6, UC8)
**Актор**: Система
**Действия** (автоматические):
1. Система создает permissions для участников:
   - `CASES:{caseId}:READ` для всех участников
   - `CASES:{caseId}:CLUES_ADD` для investigator_1
   - `CASES:{caseId}:CLUES_UPDATE` для officer_1
   - `CASES:{caseId}:UPDATE` для создателя (dispatcher)

**Проверки**:
- Permissions созданы в таблице user_permissions
- Каждый участник видит дело в своем списке `/cases`

---

#### Шаг 5: Сбор улик следователем (UC2)
**Актор**: Следователь (investigator_1)
**Действия**:
1. Авторизация как `investigator_1`
2. Переход в `/cases`
3. Открытие дела "Расследование кражи"
4. Переход на `/clues/new?case_id={caseId}`
5. Создание улики #1:
   - Title: "Запись с камеры видеонаблюдения"
   - Description: "Видео момента кражи"
   - Загрузка файла: surveillance.mp4
6. Создание улики #2:
   - Title: "Отпечатки пальцев на витрине"
   - Description: "Снятые экспертом"
   - Загрузка файла: fingerprints.jpg
7. Создание улики #3:
   - Title: "Заключение эксперта"
   - Description: "Анализ отпечатков"
   - Загрузка файла: expert-report.pdf

**Проверки**:
- Улики созданы в БД (таблица clues)
- Файлы загружены в ЦБД (таблица files)
- Metadata улик содержит ссылки на файлы (imageUris, videoUris, reportUris)
- Статус улик = PENDING

---

#### Шаг 6: Подтверждение улик офицером (UC2)
**Актор**: Офицер (officer_1)
**Действия**:
1. Авторизация как `officer_1`
2. Переход в дело
3. Просмотр списка улик
4. Просмотр каждого файла (кнопка "View")
5. Подтверждение улики #1 (изменение статуса на APPROVED)
6. Подтверждение улики #2
7. Подтверждение улики #3

**Проверки**:
- Статус улик изменен на APPROVED в БД
- Отображение обновленных статусов в UI
- Логирование действий в таблице log_entries

---

#### Шаг 7: Формирование шаблона отчета (UC3)
**Актор**: Офицер (officer_1)
**Действия**:
1. На странице дела нажатие "Create Template"
2. Переход на `/templates/new?case_id={caseId}`
3. Проверка автозагрузки данных:
   - Список участников (3 человека)
   - Список улик (3 улики)
   - Список подозреваемых (если есть)
4. Заполнение:
   - Title: "Итоговый отчет по делу о краже"
   - Description: "Отчет включает все собранные улики и показания"
5. Выбор всех участников, улик
6. Нажатие "Submit"

**Проверки**:
- Шаблон создан в БД (таблица templates)
- Автоматическая генерация markdown файла
- Файл загружен в ЦБД
- Metadata шаблона содержит:
  - `templateFileId`
  - `templateFileUrl`
  - `employeeIds` (выбранные участники)
  - `clueIds` (выбранные улики)
- Статус шаблона = CDB_ADDED

---

#### Шаг 8: Сохранение отчета в ЦБД (UC12)
**Актор**: Система
**Действия** (автоматические):
1. При создании шаблона система:
   - Генерирует markdown контент
   - Создает Blob с типом text/markdown
   - Отправляет POST /api/files
   - Получает file ID
   - Обновляет template с cdbId и metadata

**Проверки**:
- Файл существует в таблице files
- content_type = "text/markdown"
- filename = "template_{id}.md"
- Содержимое файла корректно (таблицы с users, clues, suspects)
- Возможность скачать файл через download_url

---

#### Шаг 9: Уведомление участников (UC4)
**Актор**: Система
**Действия** (автоматические):
1. При создании дела → уведомление всем участникам
2. При добавлении улики → уведомление создателю дела и ответственному
3. При изменении статуса дела → уведомление всем участникам
4. При создании шаблона → уведомление всем участникам

**Проверки**:
- Уведомления созданы в таблице notifications
- Каждый участник видит уведомления в `/notifications`
- Счетчик непрочитанных обновляется
- WebSocket отправляет real-time уведомления

---

#### Шаг 10: Просмотр данных участниками (UC9, UC11)
**Актор**: Все участники (dispatcher, officer_1, officer_2, investigator_1)
**Действия**:
1. Каждый участник авторизуется
2. Переход в `/cases`
3. Открытие дела "Расследование кражи"
4. Проверка корректности отображения:
   - Основные данные дела (title, description, status)
   - Связанный инцидент
   - Список участников и их позиции
   - Список улик с файлами
   - Шаблоны отчетов
5. Скачивание файлов улик
6. Скачивание шаблона отчета из ЦБД

**Проверки**:
- Все данные согласованы между участниками
- Каждый участник видит одни и те же данные
- Файлы скачиваются корректно
- Нет "висячих" улик (все имеют case_id)

---

#### Шаг 11: Логирование действий (UC10)
**Актор**: Администратор (admin)
**Действия**:
1. Авторизация как `admin`
2. Переход на `/logs`
3. Просмотр журнала аудита
4. Проверка наличия записей для:
   - Создания инцидента (CREATE INCIDENT)
   - Создания дела (CREATE CASE)
   - Добавления улик (ADD CLUE x3)
   - Изменения статусов улик (UPDATE CLUE x3)
   - Создания шаблона (CREATE TEMPLATE)
   - Загрузки файлов (UPLOAD FILE x4)

**Проверки**:
- Все действия залогированы в таблице log_entries
- Каждая запись содержит:
  - user_id (кто выполнил)
  - timestamp (когда)
  - action (что сделано)
  - entity_type и entity_id (с чем работали)
  - details (дополнительная информация)
- Возможность фильтрации по дате, пользователю, типу действия

## 5. Верификация конечного результата

### 5.1 Проверки через UI
**Что проверяем**:
- Офицер может скачать итоговый отчет из `/cases/{id}`
- Содержимое отчета корректно (все выбранные данные присутствуют)
- Все участники видят одинаковое состояние дела
- Хронология событий корректна

### 5.2 Проверки через SQL
**Запросы для верификации**:

#### Проверка целостности данных
```sql
-- Нет улик без дела
SELECT COUNT(*) FROM clues WHERE case_id IS NULL;
-- Должно быть 0

-- Все участники дела имеют permissions
SELECT u.username, c.case_id, up.privilege
FROM users u
JOIN user_cases uc ON u.user_id = uc.user_id
JOIN cases c ON uc.case_id = c.case_id
LEFT JOIN user_permissions up ON u.user_id = up.user_id
WHERE c.case_id = {testCaseId}
  AND up.privilege LIKE CONCAT('CASES:', c.case_id, '%');
```

#### Проверка логирования
```sql
-- Все ключевые действия залогированы
SELECT action, COUNT(*) as cnt
FROM log_entries
WHERE entity_id = {testCaseId}
GROUP BY action;
-- Должны быть: CREATE_CASE, ADD_CLUE, UPDATE_CLUE, CREATE_TEMPLATE
```

#### Проверка ЦБД
```sql
-- Шаблон сохранен в ЦБД
SELECT t.template_id, t.status, t.cdb_id, t.metadata
FROM templates t
WHERE t.related_case_id = {testCaseId}
  AND t.status = 'CDB_ADDED'
  AND t.cdb_id IS NOT NULL;
```

## 6. Фиксация результатов

### 6.1 Артефакты тестирования
**Что сохраняем**:
- Скриншоты UI на каждом шаге бизнес-процесса
- Логи консоли браузера (JavaScript errors, warnings)
- Сетевые запросы (Network tab → HAR файлы)
- SQL дампы состояния БД до и после теста
- Видеозапись выполнения сценария (Cypress video)

### 6.2 Отчет Allure
**Структура отчета**:
- Шаг 1: Регистрация вызова → PASSED/FAILED
- Шаг 2: Автоназначение → PASSED/FAILED
- ...
- Шаг 11: Логирование → PASSED/FAILED
- Общее время выполнения
- Список найденных дефектов

### 6.3 Регистрация дефектов (Jira)
**При обнаружении несоответствия**:
- Создаем задачу в Jira
- Указываем:
  - Нарушенный Use Case (например, UC2)
  - Функциональное требование из SRS
  - Шаги воспроизведения (последовательность действий в UI)
  - Ожидаемое поведение
  - Фактическое поведение
  - Приоритет (Blocker, Critical, Major, Minor)
  - Скриншоты/видео

## 8. Регрессионное тестирование

### 8.1 Когда запускать
- После исправления любого дефекта
- Перед каждым релизом
- После изменений в API
- После обновления зависимостей

### 8.2 Что проверять
- Полный основной сценарий (Сценарий 1)
- Все критические пути
- Ранее найденные и исправленные баги

### 8.3 Автоматизация
**Цель**: 100% автоматизация регрессионных тестов
- Все E2E сценарии в Cypress
- Интеграция с CI/CD (запуск на каждый commit в main)
- Ночные прогоны полного набора

---

## 9. Критерии приемки E2E тестов

**Тесты считаются пройденными, если**:
- ✅ Основной бизнес-сценарий выполнен от начала до конца без ошибок
- ✅ Все данные корректно сохранены в БД
- ✅ Все участники видят согласованное состояние дела
- ✅ Логирование зафиксировало все ключевые действия
- ✅ Файлы корректно сохранены и доступны в ЦБД
- ✅ Уведомления отправлены всем участникам
- ✅ Нет "висячих" данных (orphaned records)
- ✅ Время выполнения основного сценария < 5 минут

**Критерии провала**:
- ❌ Любой шаг основного сценария не выполнен
- ❌ Данные несогласованы между участниками
- ❌ Отсутствуют логи критических действий
- ❌ Файлы не сохранены в ЦБД
- ❌ Уведомления не отправлены
